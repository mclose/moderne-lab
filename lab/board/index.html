The same security fix asked of Copilot coding agents again and again, next to one OpenRewrite recipe. Every run started from the same commit in a fresh session with the same prompt. Runs were made on 2026-10-30 with the Copilot CLI 1.0.105.

Over — agent runs on — models, the agents wrote — different fixes for one planted log4j-core 2.14.1. The recipe wrote — fix, the same bytes all five times.

What happened, in order

  1. Every run fixed Log4Shell. All 40 agent builds and the recipe's build passed, and every log4j-core version they resolve to is past the Log4Shell fixes.
  2. The recipe wrote one fix, the same bytes five times: bump to 2.26.1. Run again on its own result, it found nothing left to change. This is the canary: a well-known CVE with a one-line fix, and the recipe fixed it.
  3. The agents wrote six different fixes. Sonnet, Haiku and MAI each repeated one patch exactly. The other five models changed approach between fresh sessions with the same prompt. Chart: “Which fix each run chose”.
  4. The differences matter later, not today. 21 runs deleted the dependency and 10 left the version to Spring Boot. The recipe has nothing to change in those, but nothing stops 2.14.1 coming back either. The 7 runs that pinned 2.17.2 are safe today, and the recipe would still move them to 2.26.1.   5. Cost varied 35× for the same result, from 3 credits for Haiku's five runs to 106.5 for grok's. Chart: “Cost for five runs”.

Bottom line: everyone got this one right. The drift is in how they fixed it, not whether they did. Lab 8b is where that stops being true.

What happened, in order

40 agent runs (eight models, five each) and the recipe, then 30 more runs with one extra line in the prompt.

  1. Every build passed, agents and recipe alike. ./mvnw verify runs the unit tests, but it never starts the app, so it said “done” for every patch.
  2. Then each app was started and attacked, and 12 of 45 wouldn't start. That was all five recipe runs (one patch, five times), 4 grok runs, 2 Sonnet runs and 1 MAI run. Every one of them had upgraded commons-configuration2 to 2.15.1. Every run that chose 2.12.0 or older, or removed the library, started. Chart: “The upgrade that stops the app”.
  3. A run that won't start can't be probed. In the grid below, those rows have a red Starts cell followed by faded grey cells. Grey doesn't mean the attack failed; it means there was nothing to attack.
  4. So the recipe as shipped failed. Its patch breaks the app, and in production that's an outage. That's the recipe's red row at the top of the grid.
  5. The recipe's code changes did work. The next row down is the recipe's code changes with commons-configuration2 left at 2.7, from the harness's first test run, so the app starts. It closed 4 of 7 holes, including the StAX XXE that 31 of the 33 agent runs that started missed. It missed the SAX XXE and both SQL injections. It's an earlier, separate build, not the shipped patch.
  6. The agent runs that started fixed what the ticket named. All 33 closed the DOM XXE, Text4Shell, Zip Slip and both SQL injections, including the copy-pasted one the ticket didn't mention. 31 of them left both unnamed XXEs (StAX and SAX) open. Only Sonnet clones 2 and 3 closed all seven.
  7. No two of the 40 agent patches are the same. Haiku and MAI repeated one Log4Shell patch exactly, but here they wrote five different patches each. On a one-line fix they look deterministic; on a real ticket they drift like the rest. Different patches still often led to the same probe result: every Haiku, gpt-6-luna and kimi-k3 run scored the same.
  8. Cost doesn't buy safety here. Haiku's five runs cost 7.4 credits and grok's 320. Both left the unnamed XXEs open, and only grok's broke startup. Chart: “Cost for five runs”.
  9. One line in the prompt stopped the outage, but not the gaps. Asked to start the app before finishing, all 30 runs on six models did, and all 30 started, against 27 of 30 without the line. Three Haiku runs still chose 2.15.1, hit the startup error and fixed the code around it. Both unnamed XXEs stayed open in 27 of 30, and credits went up about a third. Table: “Does one line in the prompt fix it?”.
  10. The canary holds. The DOM XXE, Text4Shell and Zip Slip were closed by every run that started and by the recipe's code. So the tooling and the probe were working, and the gaps are real.

Bottom line: nothing here was safe on its own. The recipe was consistent, the same bytes every time, but this time consistently broken. The agents were inconsistent and sometimes right. Without being told, almost no agent (1 of 40) and not the recipe started the app before calling the job done; told to, every agent did, and the outage went away. Neither change made anyone look past the ticket.

Lab 8 · Log4Shell

  • Target: spring-petclinic-microservices at e8b747ab, with log4j-core 2.14.1 planted in customers-service. Five clones, all at the same baseline commit.
  • Agent prompt, word for word: “Our security scanner flagged CVE-2021-44228 (Log4Shell) in this repo. Fix it so the build still passes.”
  • Recipe: lab.FixLog4Shell, one UpgradeDependencyVersion to 2.26.1, run with the Moderne CLI 4.12.0.
  • Every result was built with ./mvnw verify, inventoried with DependencyInsight, and then had the recipe run on top of it.

Lab 8b · Scanner ticket

  • Target: a five-module Spring Boot 4 ledger app written for this lab in three team styles. No model can have seen it before.
  • The prompt is a scanner report with five findings and line numbers. It doesn't mention the StAX XXE, the SAX XXE or the copy-pasted SQL injection.
  • Recipe: lab.LedgerScannerFindings (dependency upgrades plus rewrite-java-security's XXE, Zip Slip and SQL injection recipes). The Moderne CLI refused this private repo, so it ran with the free OpenRewrite Maven plugin 6.46.1.
  • The probe is kept outside the repo, so no agent can fix to the test.

What to keep in mind

  • Five runs per model is a small sample. It shows that drift happens and what shape it takes, not how often each fix appears in general.
  • Every model ran at medium reasoning effort, except kimi-k3, which rejects that setting and ran at its own default.
  • Runs that broke startup can't be probed, so whether their code fixes worked is unknown. Their patches are kept as written: no agent output was edited.
  • The first Lab 8 cross-check pass for the panel models failed because the recipe wasn't installed, and the harness recorded the failures as “nothing to change”. Those results were thrown out and rerun after the harness was fixed.
  • Side B ran before Side A, and the clones were scrubbed of all ignored files (including the recipe's own patch) before every agent session.
